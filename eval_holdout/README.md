# Независимый контрольный набор (holdout)

Набор создан отдельно от разработки агента проверки требований: автор не видел код и данные агента, агент на этом наборе не настраивался.

- `holdout_installments.md` (рассрочка 0-0-12, нумерованные ФТ/НФТ): 16 дефектов, 6 корректных требований.
- `holdout_deposit.md` (онлайн-депозит, часть требований без номеров): 15 дефектов, 6 корректных требований.
- Разметка: `*.labels.json` (дословные цитаты, номера строк, тип, критичность).
- Типы дефектов, рассрочка: api 2, contradiction 2, incomplete 3, ambiguity, non_singular, regulatory, units, design_in_req, unverifiable, security, empty_section, no_version по 1.
- Типы дефектов, депозит: api 3, incomplete 3, contradiction 2, non_singular, units, ambiguity, security, unverifiable, design_in_req, empty_section по 1.
- Корректные требования нужны для замера ложных срабатываний.

## Результаты (модель gemini-3.5-flash-lite, 26.11.2026)

| Прогон | Найдено дефектов | Точность находок | Ложные critical/major на корректных требованиях | Дефектов с вопросом автору |
|---|---|---|---|---|
| Первый прогон, агент набор не видел | 29/31 (94%) | 84% | 1 | 28/31 |
| После исправления одной ошибки кода* | 30/31 (97%) | 86% | 1 | 29/31 |
| После исправления Reviewer по разбору ошибок** | 30/31 (97%) | 89% | 1 | 30/31 |
| После слияния повторов между агентами*** | 30/31 (97%) | 88% | 1 | 29/31 |
| После сведения замечаний об атомарности**** | 30/31 (97%) | 89% (по пунктам 88%) | 1 | 29/31 |

\* Правило «нет версии документа» находило дефект, но ставило ссылку на строку `status` из таблицы полей API, а не на паспорт документа. Исправлена привязка, а не детектор. Оставшийся пропуск (поле `interest_rate` в примере JSON против `rate_percent` в описании) — промах модели, под набор не подгонялся.

\*\* Причину нашли разбором ошибок на обоих наборах, а не подгонкой под этот: если из одного абзаца выделено несколько требований, Reviewer видел у всех один и тот же текст и помечал их как дубли друг друга. Теперь каждое требование получает свою формулировку (см. раздел «Разбор ошибок» в корневом README).

\*\*\* Код сливает находку Reviewer и находку ConsistencyReviewer об одном дефекте. Удалены 4 повтора верных находок, которые метрика считала попаданиями, поэтому точность снизилась на 1 п. п.; находок вне разметки столько же. Вопросы задаются по меньшему числу находок, и по одному дефекту вопроса не стало.

\*\*\*\* Если в документе два и больше незначительных замечания «Единичность», код сводит их в одну находку со всеми требованиями и цитатами (как уже было с «требованиями без идентификатора»). На депозите 2 таких замечания стали одним, на рассрочке 3 — одним. Отметка ❌ и балл каждого требования не меняются, полнота та же. Рост точности на 1 п. п. — эффект метрики: если сводную находку считать по пунктам, точность 88%, как до сведения. Набор при этом не подгонялся: причину шума нашли разбором ошибок на обоих наборах.
